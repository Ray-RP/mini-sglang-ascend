## 1. Scope

**v0.2.0a1 candidate scope:** Mini-SGLang Ascend fixed-TP2
adaptation for Qwen3-0.6B, Qwen3-1.7B, and Qwen3-4B under the
eager `npu_fia` bf16 greedy envelope.

Everything outside this exact envelope is out of scope for the
candidate — see §7 (Known limitations) and §8 (Non-claims).

## 2. New since v0.1.0a1

User-visible changes since the prior technical-preview tag
`v0.1.0a1` (`a09efd3`, 2026-07-06):

* Fixed-TP2 bring-up path for Ascend 910B1, exercised
  end-to-end via `torchrun --nproc_per_node=2` under the
  `npu_fia` attention backend, HCCL primary + gloo sidecar
  collectives, `use_pynccl=False`, and eager execution.
* Qwen3-0.6B TP=2 functional coverage across the six-case
  matrix (A / B / C / D / E / F).
* Qwen3-1.7B TP=2 functional coverage across the six-case
  matrix (A / B / C / D / E / F).
* Qwen3-4B TP=2 functional coverage across the six-case
  matrix (A / B / C / D / E / F).
* Unified three-model fixed-TP2 capability matrix — all three
  models run through the same driver on the same rig under the

  Gate 5.1 – 5.7 evidence into a single reviewer entry point.
* Release-readiness audit (Gate 5.9) — documentation-only, no
  runtime change, feeds this RC.

There is **no performance-superiority claim** and **no
benchmark update** in this candidate. There is no cross-stack
comparison (SGLang / vLLM / TGI / TensorRT-LLM). See §8.

## 4. Supported envelope

The candidate is supported under exactly this envelope:

| Knob | Value |
|---|---|
| Parallelism | TP = 2 (`torchrun --nproc_per_node=2`) |
| Execution mode | eager |
| Attention backend | `npu_fia` |
| dtype | bf16 |
| Sampling | greedy |
| Distributed collectives | HCCL primary + gloo sidecar; `use_pynccl=False` |

**Evidence hardware environment:** 2 × Ascend 910B1 (64 GiB HBM
each), torch 2.4.0, torch_npu 2.9.0.post1, CANN 8.5.1,
Python 3.11.14.

The evidence hardware is the environment on which every Gate
4.1 – 4.14 and Gate 5.1 – 5.7 record was produced. It is stated
here for reproducibility; the RC does **not** promise
generalisation to other Ascend SKUs, other driver stacks, other
CANN versions, other torch / torch_npu versions, or other
container images.

## 5. Supported models

The candidate lists exactly three supported dense Qwen3 models:

* Qwen3-0.6B
* Qwen3-1.7B
* Qwen3-4B

Deliberately **not** listed and **not** supported by
`v0.2.0a1`:

* Qwen3-8B
* Qwen3-14B
* Qwen3-32B
* MoE variants (Qwen3-Next / Qwen3-Coder-Next / Qwen3-30B-A3B /
  Qwen3-Next-80B-A3B-* / etc.)
* Quantized variants (FP8, W8A8, INT8, INT4, …)

Any of the above would require its own bring-up gate before it
could be added to a future candidate.

## 7. Known limitations

The `v0.2.0a1` candidate does **not** and will **not** cover:

* Anything outside fixed TP=2 — no TP=1, no TP=4, no TP=8.
* Runtime TP switching between processes of different TP degree.
* TP elasticity (any form of runtime TP resize inside a live
  process).
* B > 2 (batch sizes above 2) — the release scope is exactly
  the fixed A / B / C / D / E / F six-case functional matrix.
* Qwen3-14B / Qwen3-32B claims of any kind.
* Quantized model claims (FP8, W8A8, INT8, INT4, …).
* MoE model claims (Qwen3-Next / Qwen3-Coder-Next / Qwen3-30B-A3B
  / Qwen3-Next-80B-A3B-* / …).
* Any benchmark, throughput ranking, or cross-stack comparison
  claim.
* The HTTP / ZMQ cross-process server request path — Gate 5.x
  did **not** expand server-mode coverage; the fixed-TP2 record
  is offline-driver plus committed hermetic tests only.
* Long-duration soak / rolling-allocator stability — no
  thousands-of-tick run is attached.
* Upstream merge acceptance into `sgl-project/mini-sglang`.
* **Git history hygiene remains unresolved.** The Gate 4.13a /
  4.13b redaction sweep applied to the tracked HEAD only.
  History-blob hygiene is deliberately out of scope for this
  RC. See §9 and §10.

## 10. External release blocker

**A `v0.2.0a1` tag must not be cut until the release owner
explicitly acknowledges the external credential-rotation /
git-history-hygiene risk decision.**

Concretely, the release owner must — before authorising any
release cut — take a documented position on:

* whether historical Git blobs from before the Gate 4.13b
  sweep still contain SSH / container / password substrings;
  and
* whether any credentials once present in those blobs have
  been rotated at their source (SSH host password, container
  access token, private-network endpoint, etc.); and
* whether the resulting residual risk is acceptable for a
  public technical-preview tag.

This RC does **not** perform a history rewrite, does **not**
force-push, does **not** rotate credentials, and does **not**
attempt to enumerate the historical substrings. Those actions
are strictly the release owner's authority.
